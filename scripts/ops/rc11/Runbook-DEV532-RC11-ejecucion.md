# HF One / DEV-532: ejecución humana única de RC11

Fuente: [inspección de Contabo](https://github.com/fhamann79/hfpos/issues/134#issuecomment-7025661378) y [runbook RC11](https://github.com/fhamann79/hfpos/issues/134#issuecomment-7016965462). Se mantiene `v0.1.0-rc.11`, SHA `8c80d8468834d2e8cdf6353a443ec35fa51e70ae`. No correr RC9/RC10. Solo el operador puede ejecutar y autorizar R4. No publicar logs crudos, credenciales o archivos de estado.

La protección nueva no se usa en producción desde un borrador. Debe estar revisada y autorizada, y el observador real debe cubrir ambas familias antes del corte. Las pruebas sintéticas no acreditan el preflight del host.

El preflight solo acepta el socket Unix local de Docker gestionado por systemd. Docker, Compose y el respaldo usan ese mismo endpoint sin alterar el contexto guardado. Si existe UFW, se comprueba el perfil stock Noble 0.36.2-6 (unidad vendor, IPv6, iptables-nft, sin hooks personalizados, sysctl stock o desactivado); no se instala, modifica ni recarga UFW desde el corte.

## Una ejecución desde Windows

En la misma carpeta están el lanzador, el monitor, el empaquetador y sus fuentes Python. No copie fragmentos al shell remoto ni instale nada en el VPS. El lanzador utiliza el SSH habitual con huella estricta, Python 3 existente y Docker Compose. Solicita el destino SSH de `hfadmin` y las IP **directas** IPv4 e IPv6 del VPS del inventario privado. No use IP del CDN. El monitor requiere salida local a ambas familias y una autenticación SSH fresca con la credencial local ya disponible; de lo contrario no hay prueba independiente. El túnel solo se publica en `127.0.0.1:7443`. Se requiere Docker Engine 28 o posterior para no depender del firewall para aislar un puerto publicado en loopback, y Compose con soporte de `!override`, comprobado antes de cerrar ingreso.

```powershell
& "C:\Users\fhama\.codex\visualizations\2026\06\01\019e84c0-f882-7182-af11-0fbb40868f9d\Ejecutar-DEV532-RC11.ps1"
```

1. **Antes:** el proceso muestra `GO_PREFLIGHT` solo con base, regla comprobada con `nft -c`, certificado de origen válido, SQL y productor de respaldo verificados. En el monitor deben constar TLS4/TLS6, SSH4/SSH6 y autenticación nueva. Solo entonces, si autorizas R4, escribe `AUTORIZO R4 RC11`.
2. **Cierre:** tras la autorización se comprueba la protección permanente `inet hf_one_rc11_guard` y su dependencia desde Docker. Una tabla distinta cierra TCP 443 a destino local antes del DNAT, en IPv4 e IPv6. No se reescribe UFW ni se bloquean SSH o loopback. Exige dos muestras del monitor: TCP4/TCP6 y HTTPS público **False**; SSH4/SSH6, autenticación nueva y TLS por túnel **True**. Solo entonces escribe `CIERRE DUAL CONFIRMADO`. Si no se acredita, no se drena ni se reabre automáticamente.
3. **Corte:** bajo el mismo descriptor del `flock`, detiene web/backend, exige salida limpia, comprueba cero sesiones escritoras/cola y usa la implementación conocida de respaldo (no su servicio ni timer). Coteja el servicio activo de retención, las huellas de los helpers instalados y que las raíces de respaldo correspondan a los montajes de keyring/TLS y al env canónico. Solo el adaptador usa el descriptor ya abierto y exige web/backend detenidos. Se mantienen el empaquetado, age, subida y relectura de ciphertext/manifest con hash/tamaño. El snapshot queda en la ubicación offsite y política de retención existentes; estado de captura separado del horario. Solo con marcador offsite se migra.
4. **Migración:** la lectura administrativa desde el contenedor PG se hace en READ ONLY. Se comprueba vínculo DSN y login real de `hf_one_migrator` con la lista EF (64 entradas, única pendiente aprobada); el backend sigue con su cuenta runtime. La ejecución EF es una sola invocación aprobada y se verifica historial completo posterior, cobertura RBAC y ausencia de cola incierta. Después arrancan backend y web por los digests fijados, sin reiniciar PostgreSQL ni alterar keyring/TLS. La web de prueba solo se publica en el loopback remoto; si se pierde la tabla durante esta fase, la web no queda expuesta.
5. **Apertura:** con `GO_POSTCORTE` y TLS por túnel operativo, pulsa **B** en el monitor. En el Edge privado reingresa con un ADMIN y abre ambos selectores masivos; no confirmes lotes. Cierra esa ventana y escribe `VALIDADO FUNCIONAL Y ABRIR RC11` solo si fue correcto. El procedimiento persiste configuración, vuelve a publicar la web y quita solo su tabla de mantenimiento. Confirma HTTPS de origen y público desde el monitor. No registres ventas de prueba.

Antes de quitar la cuarentena (RC11 o retorno RC8), se comprueba para cada familia que TCP/443 llega por DNAT exacto o por el `docker-proxy` propietario al endpoint web esperado en 8443. El TLS por túnel no sustituye esa prueba. Un listener ajeno o una ruta no acreditada dejan el cierre puesto.

## STOP y recuperación

- Antes de drenar, una prueba de cierre fallida deja STOP. La reconciliación no modifica ninguna tabla; si la protección permanente o la persistencia del cierre no se acreditan, conserva NO-GO incluso al poder leer el historial EF.
- Tras drenaje pero antes de intentar EF, un fallo de respaldo permite retorno únicamente en la misma sesión, tras verificar historial anterior, guardia y ambos contenedores originales detenidos limpiamente. `VOLVER A RC8` arranca backend anterior y web anterior solo en loopback; tras TLS válido pide `REABRIR RC8`. Si no se puede demostrar, conserva contención.
- Si se pierde la sesión, el mismo lanzador con `-Reconciliar` abre una conexión SSH nueva **solo de lectura**. Identifica la tabla propia, comprueba si el migrator identificado terminó y distingue historial previo, confirmado o incierto. No quita reglas ni reintenta EF. Preservar `/var/lib/hf-one-rc11-cutover` y la tabla `inet hf_one_rc11_maintenance`. Si hubo reinicio del VPS, no suponer que la tabla temporal subsiste.
- **EF previo y no intentado:** con una nueva autorización, recuperar el mismo inode de `flock`, demostrar que los originales y su env siguen intactos y seguir el retorno privado RC8 indicado arriba, nunca pasando por EF. **EF confirmada:** conservar la migración y la copia de corte, recuperar el lock, empezar por levantar/verificar RC11 en privado con los digests publicados y completar el gate funcional antes de reapertura. No volver a invocar el migrator. **EF previo tras intento, resultado incierto, migrator activo o efectos nuevos:** STOP; no reejecutar EF, no abrir ni restaurar hasta que se reconcilien el historial, el estado del migrator y los posibles efectos. El modo de reconciliación no automatiza ninguna escritura.
- Nunca borrar las tablas para recuperar SSH: ninguna bloquea SSH. La reapertura normal retira solo el cierre de mantenimiento y conserva `hf_one_rc11_guard`. Ante pérdida de SSH o cambios ajenos usar el acceso fuera de banda ya aprobado si existe; no deshabilitar UFW, reiniciar Docker ni vaciar el ruleset. Una instalación incompleta exige reconciliación; no reintentar el corte.
- En cualquier arranque de Docker, directo o activado por el socket, el `ExecStartPre` obligatorio valida el guard permanente y el marcador de propiedad y la tabla temporal exactos si hay mantenimiento. Un oneshot activo no sustituye esa verificación. Si el arranque se rechaza, conserva ambas tablas y el estado local; no omitas el gate ni borres marcadores para intentar arrancar.
